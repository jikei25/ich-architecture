3D Slicer + MONAI: the radiologist viewer and the AI blocks

The project advisor recommended 3D Slicer instead of building our own viewer, and 3D Slicer with MONAI for the AI side. Part A checks Slicer 5.12 against the D10 requirements and against OHIF. Part B answers whether Slicer already includes MONAI, reads the Slicer ↔ MONAI Label interaction diagram we received, explains why the PACS and Orthanc are still needed, and proposes how MONAI fills the AI blocks. The findings come from official documentation and source code; nothing here has been run on the project stack yet.

1Summary

Viewer (D10)

Reads from the PACS

Built in · per the docs

Slicer ships dicomweb-client (QIDO-RS, WADO-RS, STOW-RS) and supports DIMSE C-FIND, C-MOVE, C-GET and C-STORE. It reads dcm4chee with no change to the PACS.

SEG mask + SR report

Built in · better than OHIF

Since 5.12, SEG, Parametric Map and SR TID 1500 are in the Slicer core. OHIF cannot show the volumetric SR; it still has to be tried with the SR that highdicom produces.

Correct and save the mask

Built in · its strongest point

Segment Editor (paint, erase, HU threshold, islands, smoothing) and Segment Statistics (volume). Exports a new SEG and sends it to the PACS over STOW-RS or C-STORE.

Priority, alerts, SSO

Not built in · we build it

Same as OHIF. The difference: our part is a Python scripted module running inside Slicer, with no rebuild of the application as an OHIF extension needs.

Recommendation: feasible; run a PoC, then decide. Use 3D Slicer as the radiologist's reading workstation, with an "ICH Triage" Python module that talks to the AI results service. The team does not write a viewer, and our part is in Python, the language of the AI team and of MONAI Label. Two costs come with it: Slicer is installed on every workstation (no zero-footprint as with OHIF), and, like OHIF, Slicer is not approved for clinical diagnosis. The architecture does not change: AI results are still standard SEG and SR in the PACS.

AI blocks (D11)

Slicer does not include MONAI

The Slicer core only views and processes images. MONAI reaches Slicer only through extensions, and the MONAILabel extension is only a client: the model runs on a separate MONAI Label server.

The AI blocks are MONAI

The "AI inference service", "Annotation" and "Model training" blocks, abstract until now, are filled with MONAI. One hemorrhage model runs on two MONAI Label servers with two configurations.

The received diagram is Flow 3

It is the MONAI Label annotation loop (active learning): the AI runs only when a user clicks Run. Clinical triage needs the AI to run on its own when a CT arrives, so this diagram cannot replace Flow 2.

The PACS stays

The MONAI Label datastore is an image folder, and the Slicer DICOM database is one workstation's cache. Neither receives studies from the scanners, builds a worklist, keeps images for 10 years or serves many radiologists.

Recommendation. Keep the clinical layer (dcm4chee PACS, 3D Slicer + ICH Triage module for reading) and the data layer as they are. Fill the three abstract AI blocks with MONAI: an infer-only MONAI Label server in the inference layer, called automatically by the Orthanc gateway, and a research MONAI Label server in the research layer, called by 3D Slicer (MONAILabel extension) for annotation and training. The model registry is the only handoff between the two servers. The decision is recorded as D11.

23D Slicer and MONAI: who does what

3D Slicer is a desktop application (C++, Qt, VTK, ITK, embedded Python). Its core source has no MONAI and no PyTorch. MONAI is a set of PyTorch libraries for medical imaging; around it sit MONAI Label (an AI-assisted annotation server), MONAI Deploy (packaging and running models in hospitals) and the Model Zoo (model bundles). There are four ways to combine Slicer with MONAI:

Part A3D Slicer as the radiologist viewer (D10)

3What 3D Slicer is, and how it differs from OHIF

3D Slicer is an open-source platform for viewing and analysing medical images, written in C++ (VTK, ITK, CTK, Qt) with embedded Python. It runs as a desktop application on Windows, macOS and Linux. The current stable release is 5.12 (announced by Kitware on 15 July 2026), under a BSD-style licence with no restriction on commercial use. Slicer is extended with extensions or Python scripted modules. A scripted module can reach the whole scene, the Qt user interface and Python libraries such as requests, pydicom and dicomweb_client. Slicer is also the main MONAI Label client, so it already appears in the annotation block of the architecture. The Slicer core does not contain MONAI: the MONAILabel extension is only a client, and the model runs on the MONAI Label server (see section 2).

In short, Slicer is better than OHIF for images and masks (SR, mask correction, late masks) and equal to OHIF for priority and alerts: both need the AI results service plus a user-interface layer we build. Slicer is weaker than OHIF for deployment and login: it is installed on each workstation, shows no progressive slices and has no built-in OIDC.

5Where Slicer sits in the architecture

Slicer replaces the radiologist viewer block in the clinical layer (the architecture diagram now says "3D Slicer") and talks to the same things OHIF talks to: the PACS over DICOMweb, the AI results service over HTTP, and the identity provider. No other component changes.

Slicer replaces the viewer, not the PACS. Slicer has a DICOM database and a DICOM listener (C-STORE SCP), but they are one workstation's private cache, not an archive. Slicer does not take HL7 orders to build a Modality Worklist (flow 1.4), has no export rule with prior studies to the AI gateway (flow 2.1), does not run as an N+1 cluster, and has no storage lifecycle, 10-year retention, IHE audit or multi-user DICOMweb. Those stay with dcm4chee (D1). Scanners still send straight to the PACS, and Slicer fetches a study only when the doctor opens it.

Grey: clinical and login flows. Violet: AI results flow. Violet boxes are what the team builds.

There is a second way in, when the doctor picks a study from a web list (a web priority list or the RIS worklist). Slicer registers the URL scheme slicer://viewer/?studyUID=…&dicomweb_endpoint=…&access_token=… (registered automatically on Windows at install), so an "Open in Slicer" button on a web page opens that study straight in Slicer. A web list can then stay, and Slicer only needs the AI panel.

6What we build: the ICH Triage module

The module gives the radiologist the priority list and the AI panel inside Slicer. It talks to the PACS over DICOMweb and to the AI results service, whose API is designed in ich-triage.

  1. Priority listFetches the study list with AI state and shows a Qt table. The order (unconfirmed positive studies first, P4) is still decided by the server; the module only displays it.
  2. Real-time alertsA background thread reads the AI results service's event stream and puts events on a queue. A qt.QTimer on the UI thread takes them off, highlights the row in red and shows an alert. The Qt UI is updated only from the main thread.
  3. Open a studyDICOMUtils.importFromDICOMWeb(dicomWebEndpoint, studyInstanceUID), then load the series. The AI segmentation is hidden right after loading, following the "off by default" rule.
  4. AI panelShows the 4 states (not run, running, done and awaiting confirmation, no result), the volume and the model version. Confirm / Reject buttons send the decision to the AI results service.
  5. Late maskWhen the event stream reports a result for the open study, the module queries the new SEG series and adds it to the scene. The doctor does not reopen the study, unlike with OHIF.
  6. Correct and save the maskOpens Segment Editor on the AI mask, saves it as a new SEG series (the AI mask is not overwritten) and sends it over STOW-RS through the DICOM module.
  7. LoginRuns OIDC Authorization Code + PKCE through the system browser, receives the token on a loopback port and adds it to the Authorization header of dicomweb_client and the AI results service. The first PoC can skip this step.

7Reading the Slicer ↔ MONAI Label diagram

In the diagram we received, 3D Slicer on Windows is the client and the MONAI Label server (WSL2, app apps/radiology) is the server. Step by step:

StepCallWhat it means
1 · ConnectGET /info/The server lists its models, strategies and trainers. Here trainers = {}: the app has no training task
2 · Next SamplePOST /activelearning/randomThe server picks a random unlabelled image from the datastore (for example 078)
3GET /datastore/image?image=078Slicer downloads the CT volume (.nii) from the datastore
4 · RunPOST /infer/hemorrhage?image=078Sends only the ID, no upload. The server returns a 6-class label map (0–5) as .nrrd
5, 6 · Correct (optional)/infer/sam_2d, /infer/sam_3d, /infer/Histogram+GraphCutInteractive tools: click points (SAM) or draw scribbles; the server returns a mask for one label. Manual edits in Segment Editor make no server call
7 · Submit LabelPUT /datastore/label?image=078The corrected label is saved as the "final" label in the datastore. Nothing else runs
8 · TrainPOST /train/hemorrhageSlicer hides the Train button because the server has no trainer. Sent by hand, the task ends in ERROR
Five things to fix before it fits the architecture.
  • The datastore is a folder of NIfTI files. No DICOM, no studies from the scanners, no de-identification, no audit. Switch it to the Orthanc gateway's DICOMweb (de-identified copies), as Flow 3 already describes.
  • The AI runs only when someone clicks Run. ICH triage needs the AI to run as soon as a CT series is complete, before the doctor opens the study. The Orthanc gateway calls /infer automatically for this (section 11).
  • The learning loop is not closed. trainers = {} means the app declares no TrainTask for the hemorrhage model (or the server runs with skip_trainers). Add a trainer, or train outside MONAI Label and hand the bundle over through the registry.
  • The mask has 6 classes, but the gateway treats it as binary. ai_bridge.py treats every non-zero voxel as hemorrhage, so it would merge the subtypes into one. The SEG needs one segment per label 1–5 and the SR the volume of each. The AI team must confirm the label table.
  • "Submit Label" overwrites one file. Labels have no versions and there is no frozen dataset. Labels must be saved as DICOM SEG through the gateway and copied to the research bucket, and datasets frozen by version as in Flow 3.

8Proposed architecture

The clinical and data layers stay as they are. Two MONAI Label servers run the same app (the same hemorrhage model) with different settings, each in its own network layer.

Blue: clinical. Violet: AI inference (the automatic triage flow). Pink: research (the annotation loop of the received diagram). The rest of the architecture (Keycloak, HIS/RIS, SeaweedFS, PostgreSQL, backup) is unchanged and not redrawn here.

  1. Flow 2 · automatic triageWhen a CT series is complete, the AI worker (in staging it runs as the ai_bridge.py plugin inside Orthanc) sends the volume to the inference MONAI Label server, receives the 6-class mask, builds a DICOM SEG (one segment per subtype) and an SR (the volume of each), and sends them to the PACS over C-STORE. The doctor sees the result in 3D Slicer without clicking Run.
  2. Flow 3 · annotation and trainingThe received diagram, except that the datastore is the Orthanc DICOMweb (de-identified copies). Annotators use 3D Slicer + the MONAILabel extension: Next Sample, Run, correct with SAM, scribbles or Segment Editor, Submit Label. Labels are saved as SEG on the gateway and copied to the research bucket; the app's trainer trains a new model on a frozen dataset.
  3. Model handoffA new model is registered in the registry as a MONAI bundle with its version, metrics and approval status. The inference server loads only an approved bundle and writes its version into every SEG and SR.

9Do we still need the PACS and Orthanc?

MONAI Label and 3D Slicer both keep images somewhere, but neither can do the PACS's job:

JobPACS (dcm4chee)MONAI Label datastoreSlicer DICOM database
Receive studies from many scanners (C-STORE)YesNo: it only reads a folder or another server's DICOMwebHas a listener, but for one workstation
Worklist from HIS orders (MWL, flow 1.4)YesNoNo
DICOMweb for many radiologists at onceYesNoNo
Push series to the AI gateway (flow 2.1)Yes, export rulesNoNo
10-year retention, lifecycle, backupYes (with SeaweedFS and the cloud)NoNo: a cache, best cleared per session

When the PACS could go. Only if the project were narrowed to a research and annotation tool: 3D Slicer + MONAI Label on a public dataset (for example CT-ICH from PhysioNet), with no real studies from scanners. The project would then no longer be a triage system in a hospital. With the current scope (CTs go to the PACS, doctors read, the AI flags suspected hemorrhage), the PACS is required. This is a scope decision to agree with the advisor.
Why the Orthanc gateway stays between the PACS and MONAI. The points below cover the gateway and the AI worker next to it; in staging it runs as the ai_bridge.py plugin inside Orthanc.
  • It triggers the AI. MONAI Label runs only when something calls /infer. Orthanc receives the series the PACS pushes and raises an event when the series is complete; the AI worker then calls MONAI.
  • It converts formats. DICOM to NIfTI for MONAI, and the NIfTI mask to DICOM SEG, SR and the priority flag for the PACS and Slicer.
  • The AI has no PACS account. Results reach the PACS through Orthanc, by C-STORE to an AE that only accepts stores.
  • It is the only de-identification point. The research MONAI Label server reads only de-identified copies on Orthanc and never reads the PACS.
  • It keeps a working copy away from the PACS. Preprocessing, retries and re-runs after a model change put no load on the PACS doctors are using.

11Gateway ↔ MONAI contract

In the MONAI Label source, POST /infer/{model} takes either image (an image ID in the datastore) or file (an uploaded volume), plus params as JSON. The output parameter picks what comes back: image returns only the mask file, json only the parameters, dicom_seg a DICOM SEG (needs a DICOMweb datastore and label_info), and the default a multipart response with both. In params, result_extension chooses the mask file format (.nii.gz or .nrrd). So there are two ways to connect the gateway to MONAI:

OptionCallProsCons
A · upload the volume (use now)POST /infer/hemorrhage?output=image, multipart file=series.nii.gz, params={"result_extension": ".nii.gz"}Keeps the "NIfTI in, mask out" contract that ai_bridge.py and nifti_bridge.py already implement; the inference server needs no datastoreEach call sends the whole volume over the network (tens of MB, inside one VLAN)
B · send only the ID (as in step 4 of the diagram)The server runs with --studies set to the Orthanc DICOMweb; the gateway calls POST /infer/hemorrhage?image=<SeriesInstanceUID>Matches the "AI reads from the gateway over DICOMweb" model of Flow 2The inference server keeps a cache of identified images; needs a DICOMweb datastore with authentication
# Sketch, not run: a new segment() in ai_bridge.py for option A
def segment(volume):
    response = requests.post(
        f"{MONAI_URL}/infer/hemorrhage", params={"output": "image"},
        files={"file": ("series.nii.gz", gzip.compress(volume.to_bytes()), "application/gzip")},
        data={"params": json.dumps({"result_extension": ".nii.gz"})},
        timeout=AI_TIMEOUT_SECONDS)
    response.raise_for_status()
    return nib.Nifti1Image.from_bytes(gzip.decompress(response.content))
# mask_to_seg: one SegmentDescription per label 1–5 present, instead of a single "hemorrhage" segment
To check in the PoC. The returned mask must be on the same grid (shape, affine) as the volume sent; ai_bridge.py already rejects a mask on a different grid. If the app resamples or reorients, fix the app's post-processing, not the gateway.
