3Where Slicer sits and what we build

Slicer replaces the viewer, not the PACS: its DICOM database is one workstation's cache, with no worklist, export rules, retention or audit. It talks to the PACS over DICOMweb, to the AI results service and to Keycloak.

Grey: clinical and login flows. Violet: AI results flow. Violet boxes are what the team builds.

The ICH Triage module, designed in ich-triage, adds:

  • Priority list and alerts from the AI results service's event stream; the Qt window is updated only from the main thread.
  • Open a study with DICOMUtils.importFromDICOMWeb, the AI mask hidden after loading.
  • AI panel: the 4 AI states, volume, model version, Confirm and Reject.
  • Late mask: added to the open study when its event arrives.
  • Correct and save in Segment Editor as a new SEG over STOW-RS; the AI mask stays.
  • Login with OIDC and PKCE through the system browser; the first PoC can skip it.
  • Open from a web list through the slicer:// URL scheme, so a web priority list can stay.
Part BMONAI for the AI blocks (D11)

4The diagram we received

It is the MONAI Label annotation loop: 3D Slicer on Windows calls a MONAI Label server in WSL2 (app apps/radiology). Next Sample picks an image from a NIfTI folder, Run returns a 6-class mask, Submit saves it as the "final" label, and Train is hidden because the app has no trainer. Five gaps, all closed by the proposal:

  • The datastore is a NIfTI folder. It becomes the research Orthanc over DICOMweb, de-identified data only.
  • The AI runs only on Run. The AI worker calls it for every study, and that result is the draft.
  • There is no trainer. hemorrhage_dev has one.
  • Submit overwrites one file. Every save becomes a new SEG version with its author and status.
  • The gateway merges the 6 classes. The SEG gets one segment per subtype, once the AI team supplies the label table.

Two other ways to use MONAI were set aside: MONAIAuto3DSeg runs the model inside Slicer, so every workstation needs a GPU and the AI runs only after the doctor opens the study; MONAI Deploy remains the production path for inference.

5Proposed architecture

Keycloak, HIS/RIS, SeaweedFS, PostgreSQL and backup are unchanged and not drawn.

  1. 1 · CT to the gatewayThe PACS pushes each CT series once to the gateway Orthanc.
  2. 2 · AI on every studyThe AI worker sends a NIfTI volume to hemorrhage_approved and gets a mask back.
  3. 3 · Result to the radiologistThe mask becomes SEG and SR in the PACS. No one clicks Run.
  4. 4 · Annotators fix the draftFor research cases, the gateway stores a de-identified copy of the CT and the mask (marked draft) on the research Orthanc. The annotator opens it through hemorrhage_dev, fixes it, and each save is a new unreviewed version.
  5. 5 · Optional: a radiologist's fixSaved to the PACS while reading, it reaches the research Orthanc through the gateway as "radiologist, not reviewed".
  6. 6 · Review, train, releaseA reviewer marks one version per case reviewed. Training freezes a list of the reviewed labels and publishes a candidate bundle; only an approved bundle becomes hemorrhage_approved.
Two rules. Renaming: Orthanc draws new random UIDs on every anonymisation, so the gateway derives each new UID from the original with a keyed hash (2.25. + HMAC). A CT and all its masks then line up, and the research side cannot reverse the mapping. Drafts: only training cases get one; validation and test cases are labelled blind, and every label records the model that drafted it.

Why the PACS and the gateway stay. No MONAI or Slicer component receives studies from scanners, builds worklists, keeps images for 10 years or serves many radiologists, so the PACS stays. The gateway triggers the AI when a series is complete, converts DICOM to NIfTI and the mask back to SEG, is the only place that de-identifies, keeps a working copy off the PACS, and means the AI never holds a PACS account.

6Two MONAI Label servers

The call. The AI worker uploads the volume, POST /infer/hemorrhage_approved?output=image with the multipart field file, and gets back a mask on the same grid with the model version in its NIfTI header; the SEG records that version. Sending only an image ID instead would make the server fetch and cache identified images. Code: deploy/staging/monai and ai_bridge.py.

Why two servers. The same app runs twice with a different --conf models. Neither server keeps CT images, so splitting adds no storage, only a second process and a second copy of the model in memory. In exchange, identified volumes and annotators never meet in one process, and training cannot stop triage.

Next Sample returns only the next case's ID. When Slicer asks for the image, the research server downloads it from the research Orthanc into its cache the first time and serves it from the cache afterwards; the draft comes with it as the label the extension opens. Authentication (Keycloak) records who saved each label, and the cache is cleared nightly.

7Sites, data and failover

Every AI component is designed to survive the loss of one node and, with a second server room, the loss of a room. The clinical path does not depend on any of it: with the AI down, studies show "AI paused" and doctors read in normal order. This section is design only; staging runs on one machine.

Room A is today's server room. Room B is proposed: a second room on the campus, in another building, linked by two fibre paths. Today, losing the only room means days of restore from the cloud. The research server runs on the AI team's GPU at the HCMUT lab and reaches only VLAN 40 over a site-to-site VPN. A third location holds a small quorum witness, the cloud holds backups only, and in scenario 2 site 2 adds GPUs (keep one inference server on the campus for when the link is down). With a second room, the PACS, OpenLDAP and Keycloak need the same two-room layout, or room A stays a single point of failure for the whole hospital. Where the data lives

Two things last: the clinical record in the PACS and the labels on the research Orthanc. Research CT images are deleted once a model has been trained on them, because retraining on old images is rare and they can be fetched again from the PACS. The gateway copy is a buffer, and a frozen dataset is a list of IDs, not more images.

Fetching an image again. To retrain on a deleted case, the research server asks for it again: the PACS sends the study through the gateway, which de-identifies it with the same keyed hash, so it gets the same UIDs and its old labels still line up. This needs three things: the PACS still holds the study (10 years), the hash key never changes, and each dataset records the de-identification rule it used. Fetching many cases loads the PACS, so it runs outside reading hours.

Orthanc as an active-active gateway

Per the Orthanc Book, several Orthanc nodes can share one PostgreSQL index (Orthanc 1.9.2 and later), and with files in SeaweedFS a node keeps nothing of its own. But each node keeps its own job list and its own "series complete" timer, and its Orthanc jobs die with it. Three rules follow:

  1. Record the job from the first slice. The plugin writes a row keyed by series and model version when the first slice arrives, and the "complete" event marks it ready; two nodes still make one row. A sweep marks ready any row with no new slice for a few minutes, in case the node died right after the last slice.
  2. Workers in both rooms claim jobs with a lease. Redoing a job is safe, because the SEG UIDs depend only on the series and the model version.
  3. Results never wait in an Orthanc job. The SEG goes to the PACS with a synchronous C-STORE, and the worker retries a call that fails.

All nodes share one configuration. A database schema upgrade stops every node: the AI pauses, the clinical path does not notice. The PoC still uses an in-memory queue on one node.
