dcm4chee from end to end: how images arrive, where they live, how they leave

This page explains the PACS of the architecture, dcm4chee-arc-light 5.35.2, one flow at a time: a CT scanner storing a study, a viewer reading it, a RIS order becoming a worklist item, and the study lifecycle until its files are deleted. Every behaviour and number below was observed in the Docker Compose lab in labs/dcm4chee, which can be replayed with one script.

1The four parts of dcm4chee

dcm4chee is not one process. The archive application runs in WildFly and keeps no state of its own: what it should do comes from LDAP, what it holds is indexed in PostgreSQL, and the image files sit on a storage system. Knowing which part holds what explains most of its behaviour and most of its failure modes.

Archive application

dcm4chee-arc 5.35.2 on WildFly

Speaks every protocol: DICOM on port 11112, HL7 v2 over MLLP on 2575, HTTP on 8080 (DICOMweb, REST, web UI). Runs the background schedulers: task queue, retention, deletion, purge, worklist status.

Configuration

OpenLDAP, DICOM configuration schema

Devices, Application Entities (AEs), accepted callers, storage descriptors, retention policies, HL7 routing, scheduler intervals. Read at start and on POST /ctrl/reload. Nothing about patients is stored here.

Index and tasks

PostgreSQL, 41 tables

One row per patient, study, series and instance, the location of every file, worklist items, MPPS, and the task queue used for exports and verification. Queries (QIDO-RS, C-FIND) are answered from here only.

Image files

SeaweedFS bucket pacs, S3 API

The DICOM files themselves, one object per instance, written through Apache jclouds. Read only when pixels or full objects are requested (WADO-RS, WADO-URI, C-MOVE, export).

2Flow A · CT to dcm4chee

  1. AssociationThe scanner opens a DICOM association from its AE title (CT_SCANNER1) to DCM4CHEE on port 11112 and proposes CT Image Storage. The archive checks the calling AE title against dcmAcceptedCallingAETitle; an unknown title gets A-ASSOCIATE-RJ, reason 3 "calling AE title not recognized", before any data is sent.DICOM PS3.8 · A-ASSOCIATE
  2. C-STORE per instanceEach slice is one C-STORE request. The archive writes the object to the storage named by the AE's dcmObjectStorageID, records its MD5 digest, and adds the index rows (patient, study, series, instance, location).DICOM PS3.4 · Storage Service Class
  3. Retention dateA dcmStudyRetentionPolicy whose condition matches (here SendingApplicationEntityTitle=.*_SCANNER1) sets study.expiration_date to the receive date plus dcmRetentionPeriod (P10Y).
  4. Queryable immediatelyEvery stored instance is visible to QIDO-RS and C-FIND as soon as its transaction commits; the archive does not wait for the series to finish. In the lab, a poller saw the instance count rise from 6 to 42 while a scanner sent one slice every 0.15 s.
  5. Export rules (architecture, not in this lab)Once a series stops receiving instances for a configured time, export rules can push it to other AEs, such as the AI gateway. This is the step that starts Flow 2 on the architecture page.

3Storage: what must be set up

The archive image ships with one file system storage, fs1 (file:///storage/fs1/). Moving image files to object storage takes three pieces, all applied by labs/dcm4chee/config/ldap/s3-storage.ldif.in:

  1. A bucket and a key pairSeaweedFS gets bucket pacs and an S3 identity allowed to write it. The key pair is generated at install time and never written into the repository.
  2. A storage descriptor in LDAPAn entry dcmStorageID=s3 under the archive device with dcmURI: jclouds:s3:http://seaweedfs:8333, dcmDigestAlgorithm: MD5, dcmInstanceAvailability: ONLINE, and storage properties: container=pacs, jclouds.s3.virtual-host-buckets=false (path-style addressing, needed for SeaweedFS), a region, and the identity and credential.
  3. Point the AE at itdcmObjectStorageID: s3 on AE DCM4CHEE. Other AEs can point at other storages; the lab later shows the descriptors through GET /storage.
How a file is removed. Deleting an instance never deletes its file directly. The index row goes, its location row is marked status 1 (to delete), and PurgeStorageScheduler removes the object from the bucket on its next run (dcmPurgeStoragePollingInterval, 5 minutes by default). The index is updated first, so an interrupted purge leaves an unreferenced file in the bucket rather than an index row without a file.

4Flow B · Viewer reads a study

A DICOMweb viewer such as OHIF never touches storage or the database. It talks HTTP to /dcm4chee-arc/aets/DCM4CHEE/rs; the archive answers searches from PostgreSQL and fetches pixels from SeaweedFS.

  1. Search (QIDO-RS)GET …/rs/studies?PatientID=…, then …/series. Index only.
  2. Metadata (WADO-RS)GET …/series/{uid}/metadata returns every attribute of every instance as DICOM JSON, without pixels (106 KB for 40 slices). The viewer sorts slices and builds the volume from this.
  3. Pixels (WADO-RS)GET …/instances/{uid}/frames/1 returns raw pixel data as multipart; the viewer decodes and windows it in the browser. …/rendered returns a PNG windowed on the server, used for thumbnails.
  4. Whole object (WADO-URI)GET …/wado?requestType=WADO&…&contentType=application/dicom, the older single-object retrieve, still used by some viewers and by scripts.

OHIF in the lab. OHIF is served on 127.0.0.1:23000. Its nginx also proxies /dcm4chee-arc/ to the archive, so the browser sees one origin and the archive needs no cross-origin (CORS) configuration. The study list, the 2D viewer and the MPR layout (axial, sagittal, coronal from the 40 thin slices) all load from dcm4chee over DICOMweb. In production the same role is played by the reverse proxy in front of the archive, together with Keycloak tokens, which this lab leaves out.

5Flow C · HL7 order to worklist

The modality worklist (MWL) lets the scanner pick the patient and procedure from a list instead of typing them, so the images carry the RIS accession number and Study Instance UID. dcm4chee builds the list from HL7 v2 messages sent by the RIS to its HL7 receiver on port 2575.

  1. ADT^A04: register patientCreates the patient (PID-3 identifier, PID-5 name). The archive replies with an ACK containing MSA|AA.HL7 v2.5.1 · ADT
  2. ORM^O01: new orderTransformed by the built-in stylesheet hl7-order2dcm.xsl into a worklist item. The order control and status (ORC-1 NW, ORC-5 SC) map to SPS status SCHEDULED.IHE RAD Scheduled Workflow
  3. Route to a scannerAn hl7OrderScheduledStation entry whose condition matches (OBR-24=CT) names the device ct-scanner1; its AE title CT_SCANNER1 becomes the Scheduled Station AE Title.
  4. Scanner queries its listMWL C-FIND from CT_SCANNER1 to AE WORKLIST (not DCM4CHEE), filtered on its own station AE title. The same list is readable over HTTP at /aets/WORKLIST/rs/mwlitems.
  5. MPPS closes the stepThe scanner sends MPPS N-CREATE (in progress) and N-SET (completed), referencing the order. The worklist item moves to COMPLETED and disappears from the scanner's default query.DICOM PS3.4 · MPPS
  6. Images carry the orderEach image has the accession number, the Study Instance UID from the order, and a Request Attributes Sequence with the requested procedure ID and scheduled step ID, so the study links to the order.

6Flow D · Lifecycle and deletion

A study leaves dcm4chee in the same way whether a policy or a person decides it: it is first rejected with a Key Object Selection document carrying a rejection code (IOCM, Imaging Object Change Management), then deleted after a delay, then its files are purged. Rejected instances disappear from queries at once, so viewers stop showing them before anything is deleted.

Storage verification (POST …/studies/{uid}/stgver) re-reads every object of a study from storage and compares it with the recorded MD5; the lab study returned 42 verified, 0 failed. Running it on a schedule detects silent corruption in the bucket before a radiologist does.

8The lab and the demo

labs/dcm4chee is a separate Docker Compose project: OpenLDAP, PostgreSQL, SeaweedFS, the archive, OHIF, and two on-demand client containers that play the scanners and the RIS (dcm4che tools, and Python with pydicom and pynetdicom). All CT images are generated: a head phantom with skull, brain and a hyperdense blob, 2 localizers and 40 axial slices of 1.25 mm. A real MR study can be mounted read-only from outside the repository.

Run it
  • ./demo.sh walks through 13 steps and pauses before each one, which suits a live demo or a recording (asciinema rec -c ./demo.sh). AUTO=1 runs without pauses in a few minutes.
  • It starts from empty volumes every time, and exits with the stack still running so OHIF (http://127.0.0.1:23000) and the archive UI (http://127.0.0.1:28080/dcm4chee-arc/ui2) can be explored. docker compose down -v removes everything.
  • Secrets are generated into .env and never printed; every port listens on 127.0.0.1 only.

9Findings and pitfalls

Configuration is data, not files
Every setting is an LDAP entry with a schema. A wrong attribute name fails loudly (ldap_add: Undefined attribute type), but a setting that is valid and simply absent (for example the expired-study polling interval) silently disables the feature. Keep the site configuration as LDIF in version control and apply it with ldapmodify plus POST /ctrl/reload.
Scheduler changes apply on the next run
After a reload, a shortened polling interval takes effect only when the currently scheduled run has fired, so the first change can take up to the old interval (5 minutes) to show.
No ZDS segment, no worklist item
An ORM^O01 without a Study Instance UID in ZDS-1 is acknowledged with AA, yet no item is created; the reason appears only in the server log ("No Scheduled Procedure Steps"). The RIS integration must send ZDS, or the archive must be configured to generate the UID.
The worklist belongs to AE WORKLIST
Both MWL C-FIND and /rs/mwlitems answer on AE WORKLIST; asking AE DCM4CHEE returns 404. Completed items are hidden unless the status is asked for explicitly.
Empty values are stored as "*"
The MR sample has no accession number; the index stores * in its place. Queries and reports that read the database directly must account for it.
Deletion is deliberately slow
Reject, wait, delete, purge: four steps with their own timers. With defaults, a rejected study occupies storage for at least a day, which must be included in capacity planning, and gives a window to undo a mistaken rejection.
Viewer and archive should share an origin
Serving OHIF and DICOMweb behind one proxy avoids CORS configuration in WildFly and is the natural place for TLS and token checks.

10Not covered yet

  • Storage tiering inside dcm4chee. The architecture moves older data to cloud storage classes with rclone and bucket rules (Flow 4). dcm4chee also has its own mechanisms (several storage descriptors, a cache storage with a deleter threshold, export of studies to another storage); these were not exercised in the lab.
  • Export rules to the AI gateway and the AI result AE. Shown in the earlier proof of concept (poc/), not repeated here.
  • Security. Keycloak tokens on REST and the UI, TLS on DICOM and HL7, and audit logging are off in the lab.
  • High availability. Two archive nodes sharing LDAP, PostgreSQL and storage, as drawn on the architecture page, need a separate test.
