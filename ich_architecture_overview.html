Intracerebral hemorrhage AI system · Deployment scenario 1

System architecture: on-premise processing, cloud for storage only

The hospital already has the infrastructure it needs, so scanning, AI analysis, annotation, training and the databases all run on its own network. The cloud receives a one-way copy of studies and database backups for long-term retention (90 days to 10 years) and disaster recovery. This page shows the architecture, explains each part, and walks through how data moves.

2The seven layers

Each layer is a separate network zone (VLAN). Traffic between zones is blocked by default and allowed only for the specific connections drawn in the diagram.

VLAN 60

Management

Shared services every layer depends on: monitoring, user identity and single sign-on, the bastion host for admin access, and DNS, time sync and certificates.

VLAN 10–20

Clinical

The hospital's existing clinical systems: scanners, PACS, radiologist viewers, and HIS/RIS. This is what doctors use every day.

VLAN 30

AI inference

Receives new studies and produces the hemorrhage mask and report for emergency cases. Runs 24/7 and must stay stable.

VLAN 40

AI research

Annotation, model training and the model registry. Works only with de-identified data and has no path to the clinical systems.

VLAN 50 / 80

Data

The hospital's own storage: MinIO for image files and a PostgreSQL cluster (primary + standby) for records. VLAN 80 carries heavy storage traffic.

VLAN 70

DMZ

The only zone allowed to talk to the outside. It holds the backup gateway, firewall and VPN, and sends data out to the cloud in one direction.

Outside the hospital

Cloud

Storage only: encrypted, write-protected buckets that hold studies and database backups, moving to cheaper tiers as they age.

4Flow 1 · Emergency CT to diagnosis

This is the path shown in red. It is time-critical (target under 5 minutes from scan to AI result) and runs entirely on the hospital network.

  1. The scanner sends the studyThe CT scanner sends the finished head scan to the DICOM gateway.
    DICOM C-STORE :11112
  2. The gateway stores the official copyThe gateway forwards the original study to PACS, which remains the clinical record.
    DICOM C-STORE :104
  3. The gateway prepares the AI workIt saves a copy of the images to MinIO and notifies the AI inference service that a new study has arrived.
    S3 PUT :9000 · new-study event
  4. AI analyzes the scanThe inference service reads the image data from MinIO and runs the current validated model.
    S3 GET :9000
  5. Results go back to PACSThe hemorrhage mask (DICOM SEG) and a structured report (SR) are stored with the original study in PACS.
    C-STORE / STOW-RS :443
  6. The worklist is reprioritizedA priority flag goes to HIS/RIS so a suspected bleed moves to the top of the radiologist's worklist, and the result details are saved in PostgreSQL.
    HL7 ORU / FHIR · PostgreSQL :5432
  7. The doctor decidesThe radiologist opens the study in the PACS viewer, sees the AI mask overlaid on the scan, confirms or corrects it, and makes the diagnosis.
    DICOMweb WADO-RS
The cloud is not on this path. If the internet or the cloud provider goes down, scanning, AI analysis and diagnosis continue normally; only the cloud copy is delayed.

5Flow 2 · Annotation and model development

This is the path shown in violet. It is not time-critical and repeats over weeks and months to keep improving the model.

  1. De-identified data is preparedCopies of studies with patient identifiers removed are made available in MinIO for research use.
  2. Clinicians annotateThe annotation tool shows each scan with a draft mask from the current model. Clinicians correct the draft instead of drawing from scratch. Labels are saved back to MinIO.
    S3 GET images · S3 PUT labels
  3. A labeled dataset is frozenA versioned set of images and labels is handed to model training, so every model can be traced to the exact data it learned from.
  4. The model is trained and evaluatedTraining produces a candidate model with its metrics and publishes it to the model registry.
  5. The model is validatedClinicians and the AI team review the candidate on a held-out test set. Only an approved version is marked validated.
  6. Both sides pick up the new modelThe inference service loads the validated version for patient care. Annotation uses the latest model for better drafts, which closes the annotation loop.
Why research is separate from inference: research changes constantly and uses heavy GPU jobs, while inference must be stable and always available for emergencies. They share nothing except the model registry and de-identified data in MinIO.

6Flow 3 · Backup and replication to cloud

This is the path shown in amber. It runs in the background, is one-way, and never deletes anything in the cloud.

  1. The database is mirroredPostgreSQL primary streams every change to the standby. If the primary fails, the standby takes over within seconds.
    streaming replication
  2. Database backups are collectedThe backup gateway receives the database change log (WAL) continuously and full backups on a schedule, and sends them to the cloud. This is the only database backup, so it is monitored closely.
    pgBackRest TLS :8432
  3. New studies are copiedThe gateway copies new files from MinIO. It uses copy, not sync, so deleting something in the hospital never deletes the cloud copy.
    rclone copy · S3 :9000
  4. Data leaves through one doorEverything goes out through the firewall (HTTPS 443 only) and the encrypted VPN. No other system in the hospital can reach the internet.
    HTTPS 443 · IPsec
  5. The cloud stores it safelyStudies go to the DICOM bucket and database backups to the PostgreSQL bucket. Data is encrypted with hospital-held keys and protected by Object Lock.
    S3 PUT
  6. Data ages into cheaper tiersLifecycle rules move studies to cheaper storage over time and delete them when the retention period ends, unless they are on legal hold.
0 – 90 daysMinIO on-premise + cloud Standard
90 days – 1 yearCloud Infrequent Access
1 – 10 yearsCloud Archive
After 10 yearsDeleted, unless on legal hold

7Flow 4 · Retrieval and restore

This is the path shown as a dashed cyan line. Data comes back from the cloud only when needed, with approval and through a separate account.

Cloud backup only. There is no local backup copy, by design, for simplicity. The PostgreSQL standby covers server failures; every other database recovery comes from the cloud. Restores are slower than from local storage and need a working internet connection, so restore drills should measure the real recovery time.

9Design principles

Clinical first

Nothing outside the hospital sits on the diagnosis path. Results go to PACS so doctors keep using the tools they know.

Deny by default

Each layer is its own VLAN. Only the connections drawn in the diagram are allowed through the internal firewall.

One door out

Only the DMZ reaches the cloud, outbound only, over an encrypted VPN. The cloud can never connect into the hospital.

Research kept apart

Annotation and training use de-identified data and hand over models only through the registry.

HA is not backup

The standby handles server failure; the cloud backup handles mistakes, corruption and ransomware. Object Lock blocks deletion until retention ends.

Restore is tested

Restores are rehearsed regularly, because an untested backup cannot be relied on.
