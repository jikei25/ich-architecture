Design decisions: why each product in the architecture was chosen

2DICOM servers

The question is not "Orthanc or dcm4chee". The architecture needs a DICOM server in two places, and the requirements of the two places pull in opposite directions.

VLAN 10–20 · clinical critical path

PACS → dcm4chee

Must be durable and standards-complete: HL7 orders to a modality worklist, rule-based export with priors, a stateless cluster with persistent task queues, storage tiering and retention for 10 years, IHE audit, single sign-on. Changes rarely; owned by hospital IT.

VLAN 30 · best-effort

Gateway → Orthanc

Must be programmable and light: run code when a study is complete, de-identify fail-closed, crop and resample into a tensor and forward it (scenario 2), serve DICOMweb to annotation, scale to N+1 nodes cheaply. Changes often; owned by the AI team.

D1PACS: dcm4chee

Context. The PACS receives every study straight from the scanner, serves the viewer while series arrive, builds the scanner worklist from HIS/RIS orders, pushes selected series to the gateway, and holds the official record. The criteria below come from the flows in scenario 1.

Decision

dcm4chee as the PACS

It covers every PACS requirement in the architecture with built-in, configurable features. Nothing on the clinical path has to be custom code.

Cost accepted

Heavy to run

Java on WildFly, configuration in LDAP, more memory, a steep learning curve. Acceptable because the PACS is long-lived clinical infrastructure where completeness matters more than footprint. Mitigated by the official Docker images.

Revisit when

The hospital has its own PACS

dcm4chee is the reference choice. Any PACS that can export by rule over C-STORE and serve DICOMweb can take its place without changing the gateway, the AI or annotation.

D2AI gateway: Orthanc

Context. The gateway is the only AI-side system that talks to the PACS. It receives the export once, triggers the AI job, de-identifies fail-closed, serves de-identified studies and stores labels for annotation, returns SEG and SR to the PACS, and in scenario 2 also crops, resamples, encrypts and forwards one tensor per study to site 2.

OptionWhy it was not chosen, or why it was
AI pulls from the PACS over DICOMwebRejected. Breaks "push, don't pull": the AI would hold PACS credentials, repeated reads (preprocessing, retries, re-runs) would load the PACS hot tier, and data minimisation would depend on configuration instead of architecture.
A second dcm4chee as the gatewayRejected. dcm4chee can de-identify on export, but it cannot crop, resample, build a tensor or forward over gRPC, and extending it means Java EE development. It also needs its own WildFly and LDAP for what is only a buffer, and running the same product as the PACS loses failure isolation.
MONAI Deploy Informatics GatewayNot now. Built for routing DICOM to AI, but its standard bundle brings a message broker (RabbitMQ), object storage (MinIO by default, see D4) and MongoDB. It does not serve QIDO/WADO for annotation and has no de-identification pipeline of its own. Worth revisiting if the team adopts the whole MONAI Deploy stack.
Custom service on pynetdicomRejected. Storage SCP, stable-study detection, retries, a DICOMweb server, de-identification and HA would all be ours to write and test. Fail-closed de-identification is the most safety-critical part of the gateway and should not be rebuilt from scratch.
OrthancChosen. See the five reasons below.
  1. Programmable in placeThe Python plugin runs inside Orthanc: a stable-study callback dispatches the AI job, and the built-in /anonymize applies the DICOM PS3.15 profile. Scenario 2's crop, resample and encrypt steps are Python with numpy or SimpleITK, the same language as the AI team.
  2. DICOMweb for annotationThe DICOMweb plugin serves QIDO, WADO and STOW. MONAI Label, OHIF and 3D Slicer all work against it, and the MONAI Label documentation uses Orthanc as its reference DICOMweb server.
  3. Reuses the existing storesIndex in PostgreSQL, files in SeaweedFS through the S3 object-storage plugin. No new kind of data store is added to the Data layer.
  4. Light enough for N+1A single C++ binary that starts in seconds and needs little memory, so active-active nodes behind a load balancer are cheap.
  5. Separate failure domainA different product from the PACS, owned by the AI team. Gateway bugs, upgrades and configuration changes cannot touch the PACS; the PACS team maintains only one export rule.
Decision

Orthanc as the gateway

It provides storage, de-identification, DICOMweb and in-process scripting out of the box, which is exactly the gateway's job in both scenarios.

Costs accepted

Tags only, per-node events

De-identification edits tags only, so instances that may carry burned-in text are rejected. In active-active, each node detects stable studies on its own, so the job dispatcher must ignore duplicates per Study Instance UID.

Revisit when

Annotation load hurts inference

Add a separate research Orthanc storing into the research bucket. The PACS export rule does not change.

D3Two DICOM products, not one

Single-product optionWhat breaks
Orthanc for PACS and gatewayHL7 orders, the worklist, export rules with priors, the persistent export queue, storage lifecycle and IHE audit all become custom scripts on the clinical critical path. A gateway change made by the AI team could take down the PACS.
dcm4chee for PACS and gatewayThe AI pipeline (stable-study trigger, crop and resample, tensor forwarding, label copy to the research bucket) becomes Java EE development, and a second WildFly + LDAP stack is needed for a buffer.
dcm4chee + OrthancEach runs where it is strong. The extra cost is small, because both use the same PostgreSQL cluster (separate databases) and the same SeaweedFS cluster (separate buckets).

3Data layer

The PACS nodes and gateway nodes are stateless; all state lives in three stores, each with its own HA. The PACS is only as available as these stores, so they are chosen for durability and for being boring to operate.

D4Object storage: SeaweedFS

Context. One cluster holds the PACS bucket (every image file for the last 90 days) and the research bucket (labels and frozen datasets), plus the gateway's files. dcm4chee, Orthanc and rclone all reach it through S3. DICOM data is many small objects: a head CT is a few hundred instances of roughly half a megabyte each.

OptionAssessment
MinIORejected. The community edition lost its admin console in May 2025, stopped shipping binaries and images in October 2025, entered maintenance mode in December 2025 and was archived as "no longer maintained" in February 2026. A store that holds clinical data for years cannot depend on a project that no longer ships security fixes; the commercial successor is paid.
Ceph (RADOS Gateway)Not chosen. The most mature and feature-complete option, but it runs several daemon types (monitors, managers, OSDs, gateways), needs careful tuning and realistically a dedicated storage team. The right choice if the hospital already operates Ceph.
GarageNot chosen. Light and built for geo-distribution, but AGPL-licensed, with a smaller install base and narrower S3 feature coverage.
NFS or local disksRejected. dcm4chee and Orthanc can write to a filesystem, but a shared NFS server is a single point of failure, and the stateless-node HA model and the S3-based cloud copy both assume a distributed object store.
SeaweedFSChosen. Apache 2.0, S3-compatible, built on Facebook's Haystack design for many small files (one disk read per file, about 40 bytes of metadata per file), replication across nodes and racks, light Go binaries.
Costs accepted

Smaller project

Smaller community than Ceph, with development led by one main maintainer, and some features (for example automatic erasure-coding repair, according to a third-party review) sit in the Enterprise edition. Use replication rather than erasure coding on the free edition, and verify features before deployment.

Revisit when

Maintenance slows or Ceph exists

Every client speaks S3, so moving to Ceph RGW or another S3 store is a data copy and an endpoint change, with no application change.

D5Relational database: PostgreSQL

Context. Holds the PACS index and pending PACS work, the gateway index, AI results and label metadata, each in its own database. Keycloak needs a database too.

OptionAssessment
MySQL / MariaDBViable, not chosen. Supported by dcm4chee and Orthanc. PostgreSQL is preferred because the multi-writer TransactionMode setting the active-active gateway relies on is documented for Orthanc's PostgreSQL plugin, and because the HA and backup tools chosen in D6 and D8 are PostgreSQL tools.
Oracle / SQL ServerRejected. dcm4chee supports them, but they add licence cost and Orthanc's official index plugins target PostgreSQL and MySQL, so a second engine would be needed anyway.
PostgreSQLChosen. Supported by dcm4chee (with official Docker images), Orthanc and Keycloak, so one engine serves every database. Permissive licence, and mature failover (Patroni) and point-in-time backup (pgBackRest).
Cost accepted

One shared cluster

Every database shares one primary/standby pair, so a heavy AI query can slow the PACS index. Mitigated by separate databases, per-application connection limits and monitoring.

Revisit when

AI load hurts PACS queries

Split the AI results and label databases onto their own Patroni cluster. Applications only change their connection string.

D6Database failover: Patroni

OptionAssessment
Manual failoverRejected. Takes minutes to hours and needs an on-call database administrator, while the PACS is down for the whole time.
repmgrNot chosen. Simple, but without a consensus store it relies on a witness node and fencing to avoid two primaries after a network split.
pg_auto_failoverNot chosen. Easy to set up, but the monitor node that decides failover is itself a single point to protect.
Pacemaker / CorosyncNot chosen. Generic cluster manager; powerful but complex to configure correctly for PostgreSQL.
PatroniChosen. Leader election through a consensus store (etcd, Consul or ZooKeeper) guarantees one primary, failover takes seconds, and it is the most widely used PostgreSQL HA manager. Works with pgBackRest for rebuilding replicas.
Not drawn yet. Patroni needs a three-node consensus store (usually etcd), and clients need a way to always reach the current primary (HAProxy checking Patroni's REST health endpoint, or a floating IP). Both belong in the Data layer of the diagram.

D7PACS configuration: OpenLDAP

Context. dcm4chee keeps its configuration (devices, application entities, export rules, storage descriptors) in an LDAP directory shared by all PACS nodes. It holds no user accounts; people log in through Keycloak (D11).

OptionAssessment
Hospital Active DirectoryRejected. The dcm4che schema would have to be loaded into the hospital directory, which hospital IT rarely allows, and it would tie the PACS configuration to the identity system.
OpenDJ / Apache DSSupported, not chosen. Both are listed in the dcm4chee installation guide, but the official Docker image and most community material use OpenLDAP.
OpenLDAPChosen. The official dcm4che/slapd-dcm4chee image ships the schema, replication between providers gives HA, and the footprint is tiny.
Backup gap. The backup gateway sends PostgreSQL and image files to the cloud, but nothing in the design backs up the LDAP configuration. A scheduled LDIF export (slapcat) copied by rclone closes it; without it, a lost directory means rebuilding the PACS configuration by hand.

4Backup and cloud

HA protects against a server failing; backup protects against mistakes, corruption and ransomware. The cloud is the only backup by design, so these choices favour copies that cannot be deleted or read by anyone outside the hospital.

D8Database backup: pgBackRest

OptionAssessment
pg_dumpRejected. Logical dumps cannot restore to an exact moment, and restoring a large index from a dump is slow.
BarmanViable, not chosen. Mature and supports point-in-time recovery; cloud storage goes through separate barman-cloud tools.
WAL-GViable, not chosen. Fast and S3-native, with fewer built-in verification and repository-management features.
pgBackRestChosen. Point-in-time recovery from full, differential and incremental backups, parallel and compressed, client-side encryption, a native S3 repository, and a dedicated repository host over TLS, which is exactly the backup gateway on :8432.
Align retention with Object Lock. pgBackRest removes expired backups itself. If the bucket's Object Lock period is longer than pgBackRest's retention, the removal fails; set the two deliberately (for example both at 35 days) and alert on expire errors.

D9File copy to cloud: rclone

OptionAssessment
SeaweedFS remote syncNot chosen. Native and continuous, but it ties the backup path to the storage product chosen in D4.
Provider CLIs (aws s3 sync and similar)Not chosen. Each works with one provider, and "sync" mirrors deletions, which is exactly what the backup must not do.
rclone copyChosen. Works with any S3 store and any major cloud, copy never deletes at the destination, verifies checksums, limits bandwidth so the internet link is not saturated, and is safe to re-run.
Cost accepted

Batch, not continuous

Files written since the last run are not yet in the cloud, so the data-loss window for images equals the schedule interval. Monitor the run and the lag.

D10Cloud protection: Object Lock, hospital KMS, tiers, one door out

OptionAssessment
Tape or offline disksNot chosen. Safe from ransomware, but restores are slow and manual, and someone has to rotate the media.
Second hospital siteNot available. Scenario 1 has no second site; in scenario 2, site 2 holds only de-identified data and GPUs.
Plain cloud bucketRejected. Anyone who steals the backup credentials, including ransomware, can delete it.
Provider-managed keysRejected. The provider could decrypt patient data.
Object Lock + hospital KMS + lifecycle tiers, through one egress firewall and IPsecChosen. Write-once retention with versioning means no one can delete a copy early; keys held by the hospital mean the provider cannot read it; lifecycle tiers move studies to Infrequent Access after 90 days and to Archive after a year to cut cost; a single outbound-only door means the cloud can never connect in.
Costs accepted

Slow and strict

Archive-tier restores take hours and cost retrieval fees. Compliance-mode retention cannot be shortened even by an administrator, so retention periods must be set carefully.

Confirm with legal

Where the copies live

Check that storing encrypted copies with the chosen provider and region meets the cross-border data rules under Decree 356/2025.

5Clinical access

D11Identity: Keycloak

OptionAssessment
Each application logs in against the hospital ADRejected. No single sign-on across the viewer and tools, no built-in MFA, and every application handles passwords itself.
Cloud identity providerRejected. Puts the internet on the login path, so an outage would stop doctors from reading, against the "clinical first" principle.
Authentik / AutheliaNot chosen. Lighter, but with smaller ecosystems and no existing integration with dcm4chee.
KeycloakChosen. On-premise OIDC and SAML single sign-on with MFA (one-time codes, WebAuthn), federates users from the hospital AD so accounts stay in one place, used by dcm4chee's secured deployment, supported by OHIF, Apache 2.0 licence.
Login is on the clinical path. If Keycloak is down, doctors cannot open the viewer. It needs at least two nodes and its own database on the PostgreSQL cluster, which the High availability table does not list yet.

D12Radiologist viewer: OHIF

OptionAssessment
WeasisNot chosen. Rich desktop viewer that pairs well with dcm4chee, but it must be installed and updated on every workstation.
Orthanc viewersRejected. They read from Orthanc, which in this design is the AI gateway, not the PACS.
Commercial certified viewerKeep as an option. Certified for primary diagnosis, at a licence cost; often the hospital already has one.
OHIFChosen. Zero-footprint web viewer over DICOMweb, opens a study while series are still arriving, displays DICOM SEG and SR (the AI's outputs), logs in through Keycloak over OIDC, MIT licence, and can be extended with the confirm-or-correct workflow.
Regulatory status. The base OHIF viewer is not FDA-cleared or CE-marked, and making sure it complies with local rules is the user's responsibility. If the hospital requires a certified viewer for primary diagnosis, keep its existing one: because the AI results are standard SEG and SR stored in the PACS, any viewer that displays SEG shows them, and the rest of the architecture does not change.

6Questions reviewers ask

Is Orthanc reliable enough for a hospital?
It is not on the critical path. If the gateway stops, dcm4chee queues the export and retries, doctors read in normal order, and the viewer shows "no AI result". The gateway's reliability affects how fast the AI flag arrives, never whether a diagnosis can be made.
What if the hospital already has a commercial PACS?
Keep it. The gateway only needs the PACS to export selected series by C-STORE and to accept SEG and SR back. The gateway, AI, annotation and backup design stay the same. This is the main benefit of the push model.
Why so many open-source components? Who maintains them?
Each is a widely used tool for one job, and each speaks an open standard (DICOM, DICOMweb, S3, SQL, LDAP, OIDC). Any of them can be replaced by a commercial product with the same interface without redrawing the architecture. Who operates each one must be agreed with hospital IT before deployment.
Why not use the cloud (Google Cloud Healthcare API, AWS HealthImaging)?
The architecture processes everything on-premise and sends only encrypted copies to the cloud for retention. A cloud DICOM store would put the cloud and the internet on the diagnosis path and move identifiable data off-site, which conflicts with the design principles and with data minimisation under Decree 356/2025.
Why SeaweedFS rather than the better-known MinIO?
MinIO's community edition is no longer maintained: its repository was archived in February 2026 after a year of feature removals. SeaweedFS keeps the same S3 interface under Apache 2.0, so dcm4chee, Orthanc and rclone did not have to change.
Do the licences cause problems?
Not for internal use. dcm4chee is MPL 1.1 / GPL / LGPL. Orthanc's core is GPLv3 and its PostgreSQL and DICOMweb plugins are AGPLv3, as is Garage (not chosen). If the hospital modifies an AGPL component and lets users reach it over the network, the modified source must be offered to those users. SeaweedFS, Keycloak (Apache 2.0), OHIF (MIT) and PostgreSQL (PostgreSQL licence) are permissive.
Is active-active Orthanc actually supported?
Yes, with conditions. Since Orthanc 1.9.2 with PostgreSQL plugin 4.0, several instances can share one index. PostgreSQL plugin 6.0 with Orthanc 1.12.3 adds a TransactionMode option, where ReadCommitted lets several instances write at the same time. The shared lock must be disabled (Lock: false), and duplicate stable-study events must be filtered by the dispatcher.

7Follow-ups

Open points to close before deployment.
  • Pin the gateway versions. The High availability section cites Orthanc 1.9.2. Write down the minimum versions and settings used for active-active: Orthanc ≥ 1.12.3, PostgreSQL plugin ≥ 6.0, Lock: false, IndexConnectionsCount above 1, and the chosen TransactionMode. Test concurrent writes under load.
  • Draw the Patroni dependencies. Add the three-node etcd and the primary-routing layer (HAProxy or a floating IP) to the Data layer (D6).
  • Back up the LDAP configuration. Schedule an LDIF export and copy it with rclone (D7).
  • Make Keycloak highly available. At least two nodes, with its database on the PostgreSQL cluster, listed in the HA table (D11).
  • Align pgBackRest retention with Object Lock on the PostgreSQL backup bucket (D8).
  • Choose the SeaweedFS replication setting and confirm which features the free edition includes (D4).
  • Mark dcm4chee as the reference PACS and OHIF as replaceable by the hospital's certified viewer (D1, D12).
  • Confirm with the hospital: the existing PACS and viewer, who operates each component, and the cloud provider and region against Decree 356/2025 (D10).
