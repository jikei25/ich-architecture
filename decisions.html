Design decisions: why each product in the architecture was chosen

Each named product in the diagram is recorded here: the options considered, why each one was or was not chosen, the costs accepted, and when to revisit. Identity and the viewer are marked as placeholders still under evaluation. The dashed AI blocks (inference, annotation, training, registry) are defined by their interfaces and are not decided on this page.

2DICOM servers

The question is not "Orthanc or dcm4chee". The architecture needs a DICOM server in two places, and the requirements of the two places pull in opposite directions, so each place gets the product that fits it. Running two products costs little, because both use the same PostgreSQL cluster (separate databases) and the same SeaweedFS cluster (separate buckets).

VLAN 10–20 · clinical critical path

PACS → dcm4chee

Must be durable and standards-complete: HL7 orders to a modality worklist, rule-based export with priors, a stateless cluster with persistent task queues, storage and retention for 10 years, IHE audit, single sign-on. Changes rarely; owned by hospital IT.

VLAN 30 · best-effort

Gateway → Orthanc

Must be programmable and light: run code when a study is complete, de-identify fail-closed, crop and resample into a tensor and forward it (scenario 2), serve DICOMweb to annotation, scale to N+1 nodes cheaply. Changes often; owned by the AI team.

D1PACS: dcm4chee

Context. The PACS receives every study straight from the scanner, serves the viewer while series arrive, builds the scanner worklist from HIS/RIS orders, pushes selected series to the gateway, and holds the official record. The requirements come from the flows in scenario 1.

OptionWhy it was not chosen, or why it was
Orthanc as the PACSRejected. Orthanc has no HL7 receiver: its worklist plugin only serves .wl files from a folder, so turning HIS/RIS orders into a worklist (Flow 1.4) would be our own script. It has no export rule engine, so selecting series and priors for the AI (Flow 2.1) would be another script, and it has no rule-driven export queue that keeps retrying while the gateway is down. Storage lifecycle and retention policies are missing too. All of these would be custom code on the path doctors wait on. Orthanc is also the gateway in this design, so using it for both would let an AI-team change take down the PACS.
DicoogleRejected. An open-source archive from the University of Aveiro built around indexing and plugins, strong for research search across large archives. It does not provide HL7 order handling or a modality worklist, has no documented clustering model for N+1 nodes, and has a much smaller user base for clinical deployments.
Vendor PACSNot chosen as the reference. Certified, supported and complete, but with licence costs and lock-in, and it cannot be deployed and tested freely in a project like this. If the hospital already runs one, keep it: the design needs only rule-based C-STORE export to the gateway and DICOMweb for the viewer.
Cloud DICOM store (Google Cloud Healthcare API, AWS HealthImaging)Rejected. Puts the internet and the cloud provider on the diagnosis path and moves identifiable data off-site, against the "clinical first" and "one door out" principles and data minimisation under Decree 356/2025.
dcm4cheeChosen. Each requirement is a built-in, configurable feature; see the five reasons below.
  1. HL7 orders become the worklistThe ORM Service creates, updates and removes modality worklist items from ORM^O01 messages (order controls NW, XO, CA, SC). This is Flow 1.4 with no custom code.
  2. Export rules with priorsExport rules select what the AI receives by conditions on the study, and can add earlier studies of the same patient, for example priors=2&StudyAge=-5Y&ModalitiesInStudy=CT. This is Flow 2.1.
  3. A persistent export queueExport tasks are stored in the database and retried, so a gateway outage only delays the AI. This is the "Isolation" property of Flow 2.
  4. Built for a stateless clusterAll nodes share the PostgreSQL index, the LDAP configuration and the S3 storage, so any node can serve any request and pending work survives a node failure, as the High availability section assumes.
  5. Clinical standards and securityBroad IHE profile coverage, rejection notes, audit logging, S3 storage descriptors and retention policies, and an official secured deployment that uses Keycloak for login. Open source (MPL 1.1 / GPL / LGPL), with no licence fee.
Decision

dcm4chee as the PACS

It covers every PACS requirement in the architecture with built-in features. Nothing on the clinical path has to be custom code.

Cost accepted

Heavy to run

Java on WildFly, configuration in LDAP, more memory, a steep learning curve. Acceptable because the PACS is long-lived clinical infrastructure where completeness matters more than footprint. Mitigated by the official Docker images.

Revisit when

The hospital has its own PACS

dcm4chee is the reference choice. Any PACS that can export by rule over C-STORE and serve DICOMweb can take its place without changing the gateway, the AI or annotation.

D2AI gateway: Orthanc

Context. The gateway is the only AI-side system that talks to the PACS. It receives the export once, triggers the AI job, de-identifies fail-closed, serves de-identified studies to the annotation tool and stores the labels it saves, returns SEG and SR to the PACS, and in scenario 2 also crops, resamples, encrypts and forwards one tensor per study to site 2. The gateway does not annotate; it only serves images to the annotation tool (still to be chosen) and stores its labels.

OptionWhy it was not chosen, or why it was
AI pulls from the PACS over DICOMwebRejected. Breaks "push, don't pull": the AI would hold PACS credentials, repeated reads (preprocessing, retries, re-runs) would load the PACS hot tier, and data minimisation would depend on configuration instead of architecture.
A second dcm4chee as the gatewayRejected. dcm4chee can de-identify on export, but it cannot crop, resample, build a tensor or forward over gRPC, and extending it means Java EE development. It also needs its own WildFly and LDAP for what is only a buffer, and running the same product as the PACS loses failure isolation.
MONAI Deploy Informatics GatewayRejected. Built to route DICOM to AI workflows, but checked against its own documentation it falls short here. De-identification: its DicomDeidentifier plug-in replaces a configured list of top-level tags with dummy values before export and restores them when results return; nested sequences are not handled and it is not a DICOM PS3.15 profile, so it cannot back a fail-closed guarantee. Annotation: it has no annotation feature and does not serve QIDO-RS or WADO-RS (its API covers DIMSE, STOW-RS, FHIR and inference requests), so annotation could not read studies from it. It also brings a message broker, MinIO and MongoDB in its standard bundle, and the project is quiet: last release 0.5.2 in June 2025.
Custom service on pynetdicomRejected. Storage SCP, stable-study detection, retries, a DICOMweb server, de-identification and HA would all be ours to write and test. Fail-closed de-identification is the most safety-critical part of the gateway and should not be rebuilt from scratch.
OrthancChosen. See the five reasons below.
  1. Programmable in placeThe Python plugin runs inside Orthanc: a stable-study callback dispatches the AI job, and the built-in /anonymize applies the DICOM PS3.15 Basic Profile. Scenario 2's crop, resample and encrypt steps are Python with numpy or SimpleITK, the same language as the AI team.
  2. DICOMweb for annotationThe DICOMweb plugin serves QIDO, WADO and STOW, so the annotation tool can read de-identified studies and save SEG labels back. MONAI Label, OHIF and 3D Slicer all work against it, and the MONAI Label documentation uses Orthanc as its reference DICOMweb server.
  3. Reuses the existing storesIndex in PostgreSQL, files in SeaweedFS through the S3 object-storage plugin. No new kind of data store is added to the Data layer.
  4. Light enough for N+1A single C++ binary that starts in seconds and needs little memory, so active-active nodes behind a load balancer are cheap.
  5. Separate failure domainA different product from the PACS, owned by the AI team. Gateway bugs, upgrades and configuration changes cannot touch the PACS; the PACS team maintains only one export rule.
Decision

Orthanc as the gateway

It provides storage, de-identification, DICOMweb and in-process scripting out of the box, which is exactly the gateway's job in both scenarios.

Costs accepted

Tags only, per-node events

De-identification edits tags only, so instances that may carry burned-in text are rejected. In active-active, each node detects stable studies on its own, so the job dispatcher must ignore duplicates per Study Instance UID.

Revisit when

Annotation load hurts inference

Add a separate research Orthanc storing into the research bucket. The PACS export rule does not change.

3Data layer

The PACS nodes and gateway nodes are stateless; all state lives in three stores, each with its own HA. The PACS is only as available as these stores, so they are chosen for durability and for being boring to operate.

D3Object storage: SeaweedFS

Context. One cluster holds the PACS bucket (every image file for the last 90 days) and the research bucket (labels and frozen datasets), plus the gateway's files. dcm4chee, Orthanc and rclone all reach it through S3. DICOM data is many small objects: a head CT is a few hundred instances of roughly half a megabyte each.

OptionWhy it was not chosen, or why it was
MinIORejected. The community edition lost its admin console in May 2025, stopped shipping binaries and images in October 2025, entered maintenance mode in December 2025 and was archived as "no longer maintained" in February 2026. A store that holds clinical data for years cannot depend on a project that no longer ships security fixes; the commercial successor is paid.
Ceph (RADOS Gateway)Not chosen. The most mature and feature-complete option, but it runs several daemon types (monitors, managers, OSDs, gateways), needs careful tuning and realistically a dedicated storage team. The right choice if the hospital already operates Ceph.
NFS or local disksRejected. dcm4chee and Orthanc can write to a filesystem, but a shared NFS server is a single point of failure, and the stateless-node HA model and the S3-based cloud copy both assume a distributed object store.
SeaweedFSChosen. Apache 2.0, S3-compatible, built on Facebook's Haystack design for many small files (one disk read per file, about 40 bytes of metadata per file), replication across nodes and racks, light Go binaries. An active project with over 35,000 GitHub stars and commits every week.
Costs accepted

Smaller project than Ceph

Development is led by one main maintainer, and some features (for example automatic erasure-coding repair, according to a third-party review) sit in the Enterprise edition. Use replication rather than erasure coding on the free edition, and verify features before deployment.

Revisit when

Maintenance slows or Ceph exists

Every client speaks S3, so moving to Ceph RGW or another S3 store is a data copy and an endpoint change, with no application change.

D4Relational database: PostgreSQL

Context. Holds the PACS index and pending PACS work, the gateway index, AI results and label metadata, each in its own database.

OptionWhy it was not chosen, or why it was
MySQL / MariaDBViable, not chosen. Both dcm4chee and Orthanc support it, but Orthanc fits PostgreSQL better: the multi-writer TransactionMode setting that the active-active gateway relies on is documented for Orthanc's PostgreSQL plugin. dcm4chee's official Docker images are also built for PostgreSQL.
Oracle / SQL ServerRejected. dcm4chee supports them, but they add licence cost and Orthanc's official index plugins target PostgreSQL and MySQL, so a second engine would be needed anyway.
PostgreSQLChosen. Supported by dcm4chee (with official Docker images) and Orthanc, the best fit for the active-active gateway, and one engine for every database. Permissive licence.
Cost accepted

One shared cluster

Every database shares one primary/standby pair, so a heavy AI query can slow the PACS index. Mitigated by separate databases, per-application connection limits and monitoring.

Revisit when

AI load hurts PACS queries

Split the AI results and label databases onto their own cluster. Applications only change their connection string.

D5Database failover: Patroni

Context. The PostgreSQL primary holds the PACS index, so while it is down nothing can be stored or opened. The standby must take over within seconds, automatically, and there must never be two primaries at once: if both accepted writes after a network split, the two copies of the index would diverge and someone would have to reconcile them by hand.

OptionWhy it was not chosen, or why it was
Manual failoverRejected. Someone has to notice the failure, promote the standby and repoint every application. That takes minutes to hours and needs an on-call database administrator, and the PACS is down for the whole time.
repmgrNot chosen. Simple to set up, but it has no consensus store: each node decides on its own from what it can see. Avoiding two primaries after a network split needs a witness node plus fencing scripts that we would write and test ourselves.
pg_auto_failoverNot chosen. Easy to run, but every failover decision is made by a single monitor node. If the monitor is lost, automatic failover stops until it is rebuilt, so it becomes one more component to make highly available.
Pacemaker / CorosyncNot chosen. A generic Linux cluster manager. Powerful, but configuring PostgreSQL resources, fencing and quorum correctly is specialist work, and mistakes only show up during a real failure.
PatroniChosen. See the reasons below.
  1. One primary, guaranteedEach node runs a Patroni agent. The primary must keep renewing a leader key in a consensus store (etcd, Consul or ZooKeeper); if it cannot, it demotes itself, and only the node that wins the key may become primary. A network split cannot produce two primaries.
  2. Failover in seconds, switchover on demandWhen the leader key expires, the most up-to-date standby is promoted automatically. Planned maintenance uses a controlled switchover with no data loss.
  3. Health checks for routingA REST endpoint on each node reports whether it is the primary, so a load balancer such as HAProxy always sends applications to the right node without changing their configuration.
  4. Rebuilds replicasA failed former primary is resynchronised with pg_rewind, or a new replica is created from a pgBackRest backup (D7) instead of copying from the live primary.
  5. Backed by a wide communityStarted at Zalando in 2015 and now maintained in its own GitHub organisation under the MIT licence, with over 200 contributors, about 8,800 GitHub stars and regular releases (4.1.5 in August 2026). It is the failover engine inside the PostgreSQL Kubernetes operators from Zalando, Crunchy Data and Percona, so it is tested across a very large number of production clusters.
Not drawn yet. Patroni needs a three-node consensus store (usually etcd), and clients need a way to always reach the current primary (HAProxy checking Patroni's REST health endpoint, or a floating IP). Both belong in the Data layer of the diagram.

D6PACS configuration: OpenLDAP

Context. dcm4chee keeps its configuration (devices, application entities, export rules, storage descriptors) in an LDAP directory shared by all PACS nodes. It holds no user accounts; people log in through the identity provider (D9).

OptionWhy it was not chosen, or why it was
Hospital Active DirectoryRejected. The dcm4che schema would have to be loaded into the hospital directory, which hospital IT rarely allows, and it would tie the PACS configuration to the identity system.
OpenDJ / Apache DSSupported, not chosen. Both are listed in the dcm4chee installation guide, but the official Docker image and most community material use OpenLDAP.
OpenLDAPChosen. The official dcm4che/slapd-dcm4chee image ships the schema, replication between providers gives HA, and the footprint is tiny.
Backup gap. The backup gateway sends PostgreSQL and image files to the cloud, but nothing in the design backs up the LDAP configuration. A scheduled LDIF export (slapcat) copied by rclone closes it; without it, a lost directory means rebuilding the PACS configuration by hand.

4Backup to cloud

HA protects against a server failing; backup protects against mistakes, corruption and ransomware. The cloud is the only backup by design, so these tools must be reliable, verifiable and unable to delete what is already in the cloud.

D7Database backup: pgBackRest

Context. The PostgreSQL standby copies every mistake instantly, so recovering from a bad delete, corruption or ransomware needs a backup that can restore the database to a chosen moment. The backup gateway receives the write-ahead log continuously and full backups on a schedule, then sends them to the cloud bucket.

OptionWhy it was not chosen, or why it was
pg_dumpRejected. A logical dump is a snapshot at one moment: everything written after it is lost, it cannot restore to a chosen time, and restoring a large index from a dump takes hours of re-inserting rows and rebuilding indexes.
BarmanViable, not chosen. Mature, backed by EnterpriseDB and supports point-in-time recovery. Its main model is a backup server with local storage; sending to S3 goes through the separate barman-cloud tools, which have fewer features than its main mode. GPL-3.0. The natural fallback if pgBackRest ever stalls.
WAL-GViable, not chosen. Fast and S3-native, with good compression. It has fewer built-in tools for verifying backups and managing the repository, and less documentation for a dedicated repository host.
pgBackRestChosen. See the reasons below.
  1. Restore to any momentFull, differential and incremental backups plus a continuous write-ahead-log archive allow point-in-time recovery to just before a mistake.
  2. Fits the backup gateway exactlyA dedicated repository host pulls backups from the database servers over TLS (the backup gateway on :8432) and stores them in an S3 bucket natively, with no extra tool.
  3. Encrypted before it leavesClient-side encryption means the cloud stores only encrypted files, on top of the cloud's own encryption with hospital-held keys.
  4. Fast and verifiableParallel, compressed backup and restore, with checksums on every file and a command to verify the repository, so a broken backup is found before it is needed.
  5. Works with PatroniNew or failed replicas can be rebuilt from the repository (D5) instead of copying from the live primary.
Community risk, now addressed

It nearly stopped in 2026

pgBackRest was maintained by one person, funded by Crunchy Data. After Snowflake bought Crunchy Data, the maintainer announced on 27 April 2026 that the project would stop. On 18 May 2026 it was saved by a group of sponsors, including AWS, Percona, Supabase, pgEdge, Tiger Data and Eon.io, so it no longer depends on one company. Releases resumed: 2.59.0 in July and 2.60.0 on 18 October 2026.

Minimum version

2.59.3 or later

A security advisory on 4 October 2026 reported weak encryption subkeys and salts, fixed in 2.59.3. Because this design relies on pgBackRest's encryption, older versions must not be used.

Revisit when

Maintenance stalls again

Move to Barman. Both read the same PostgreSQL write-ahead log, so only the backup gateway changes.

Align retention with Object Lock. pgBackRest removes expired backups itself. If the bucket's Object Lock period is longer than pgBackRest's retention, the removal fails; set the two deliberately (for example both at 35 days) and alert on expire errors.

D8File copy to cloud: rclone

Context. New image files and research data on SeaweedFS must be copied to the cloud bucket, through the egress firewall, without ever deleting anything already there: if a file is deleted in the hospital by mistake or by ransomware, the cloud copy must survive.

OptionWhy it was not chosen, or why it was
SeaweedFS remote syncNot chosen. Native and continuous, but it ties the backup path to the storage product chosen in D3: replacing SeaweedFS would also mean replacing the backup.
Provider CLIs (aws s3 sync and similar)Rejected. Each works with one provider, so changing cloud means rewriting the backup. Their "sync" mode mirrors deletions, which is exactly what the backup must not do.
rclone copyChosen. See the reasons below.
  1. Never deletes in the cloudrclone copy only adds new or changed files and leaves everything else at the destination untouched. Deleting a study in the hospital cannot delete its cloud copy.
  2. Any cloud, any S3The same tool reads SeaweedFS and writes to AWS, Google Cloud, Azure or any S3-compatible provider, so the cloud provider can change without touching the backup design.
  3. Verified transfersWith --checksum it compares file hashes instead of only size and date, so a corrupted copy is detected and sent again.
  4. Gentle on the link--bwlimit caps upload speed so the backup never saturates the internet link that other hospital systems share.
  5. Backed by a very large communityMIT licence, over 60,000 GitHub stars and frequent releases (1.75.2 in October 2026). Safe to re-run after an interruption: files already copied are skipped.
Cost accepted

Batch, not continuous

Files written since the last run are not yet in the cloud, so the data-loss window for images equals the schedule interval. Monitor every run and the lag.

5Clinical access

Both decisions in this section are still open. The architecture fixes what these components must do, but the products depend on what the hospital already runs.

D9Identity: Keycloak as a stand-in

Context. Doctors log in to the viewer and clinical tools with single sign-on and multi-factor authentication. In a real deployment this will integrate with whatever identity system the hospital already has. Keycloak is in the diagram to stand for "an on-premise OpenID Connect provider with MFA", not as a final choice.

Why Keycloak as the stand-in.

  • Works with what the hospital has. It can import users from the hospital's Active Directory or LDAP, or hand login over to an existing identity provider. Applications only speak OpenID Connect, so switching to the hospital's own provider later changes configuration, not the architecture.
  • On-premise. Login is on the clinical path. A cloud identity provider would stop doctors from reading during an internet outage, against the "clinical first" principle.
  • Standard features out of the box. OpenID Connect and SAML single sign-on, MFA with one-time codes or security keys, and the login used by dcm4chee's official secured deployment. Apache 2.0 licence and a large community.
Whatever replaces it must run on-premise, support OpenID Connect and MFA, and be highly available: if login is down, doctors cannot open the viewer. The High availability table does not list identity yet.

6Questions reviewers ask

Why two DICOM servers instead of one?
Because the two roles need opposite things. Orthanc as the PACS would put custom scripts for HL7, worklist, export rules and retention on the clinical path; dcm4chee as the gateway would turn the AI pipeline into Java EE development and need a second WildFly + LDAP stack. Running both costs little because they share the same database and object store.
Is Orthanc reliable enough for a hospital?
It is not on the critical path. If the gateway stops, dcm4chee queues the export and retries, doctors read in normal order, and the viewer shows "no AI result". The gateway's reliability affects how fast the AI flag arrives, never whether a diagnosis can be made.
What if the hospital already has a commercial PACS?
Keep it. The gateway only needs the PACS to export selected series by C-STORE and to accept SEG and SR back. The gateway, AI, annotation and backup design stay the same. This is the main benefit of the push model.
Why so many open-source components? Who maintains them?
Each is a widely used tool for one job, and each speaks an open standard (DICOM, DICOMweb, S3, SQL, LDAP, OIDC). Any of them can be replaced by a commercial product with the same interface without redrawing the architecture. Community health was checked for each one (see SeaweedFS, Patroni, pgBackRest and rclone above). Who operates each one must be agreed with hospital IT before deployment.
Why SeaweedFS rather than the better-known MinIO?
MinIO's community edition is no longer maintained: its repository was archived in February 2026 after a year of feature removals. SeaweedFS keeps the same S3 interface under Apache 2.0, so dcm4chee, Orthanc and rclone did not have to change.
Do the licences cause problems?
Not for internal use. dcm4chee is MPL 1.1 / GPL / LGPL. Orthanc's core is GPLv3 and its PostgreSQL and DICOMweb plugins are AGPLv3; if the hospital modifies an AGPL component and lets users reach it over the network, the modified source must be offered to those users. SeaweedFS and Keycloak (Apache 2.0), Patroni and rclone (MIT), pgBackRest (MIT-style) and PostgreSQL (PostgreSQL licence) are permissive.
Is active-active Orthanc actually supported?
Yes, with conditions. Since Orthanc 1.9.2 with PostgreSQL plugin 4.0, several instances can share one index. PostgreSQL plugin 6.0 with Orthanc 1.12.3 adds a TransactionMode option, where ReadCommitted lets several instances write at the same time. The shared lock must be disabled (Lock: false), and duplicate stable-study events must be filtered by the dispatcher.

7Follow-ups

Open points to close before deployment.
  • Pin the gateway versions. The High availability section cites Orthanc 1.9.2. Write down the minimum versions and settings used for active-active: Orthanc ≥ 1.12.3, PostgreSQL plugin ≥ 6.0, Lock: false, IndexConnectionsCount above 1, and the chosen TransactionMode. Test concurrent writes under load.
  • Draw the Patroni dependencies. Add the three-node etcd and the primary-routing layer (HAProxy or a floating IP) to the Data layer (D5).
  • Back up the LDAP configuration. Schedule an LDIF export and copy it with rclone (D6).
  • Pin pgBackRest to 2.59.3 or later and align its retention with Object Lock on the PostgreSQL backup bucket (D7).
  • Choose the SeaweedFS replication setting and confirm which features the free edition includes (D3).
  • Choose the identity integration and the viewer with the hospital, and add identity to the HA table (D9, D10).
  • Confirm with the hospital: the existing PACS, viewer and identity system, and who operates each component.
